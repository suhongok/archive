# ROS2 콜백 방식 동작 원리

## 🎯 핵심 개념

**콜백 방식은 서비스 응답 전까지 콜백이 실행되지 않습니다.**

- ✅ 요청 전송 ← 즉시 완료
- ✅ 콜백 등록 ← 즉시 완료
- ⏳ 응답 대기 ← 콜백 **미실행**
- 🔔 응답 수신 ← 콜백 **자동 실행**

---

## ⏱️ 콜백 방식의 시간 흐름

### 타임라인

```
시간 →

[1] 요청 전송
    ↓ (비동기 - 즉시 반환)
[2] 콜백 등록
    ↓ (즉시 완료)
[3] "요청 전송 완료" 출력
    ↓
[4] while 루프 진입
    ↓
[5] spin_once() 실행 ← 응답 받을 준비
    ↓
[6] "백그라운드에서 이 코드 계속 실행 중..." 출력
    ↓
    ... 대기 중 ...
    ↓
[7] 서버가 응답 전송
    ↓
[8] ROS2가 응답 수신 감지
    ↓
[9] 콜백 함수 자동 실행 ✨
    ↓
[10] 응답 처리
```

---

## 💻 실제 코드 예시

```python
def callback(future):
    """서버 응답 후 자동으로 실행됨"""
    try:
        response = future.result()
        print(f"✅ 콜백 실행됨! 응답: {response}")
    except Exception as e:
        print(f"❌ 실패: {e}")

# ========== 이 부분이 즉시 실행됨 ==========
print("1. 요청 전송 시작")
self.future = self.client.call_async(self.req)

print("2. 콜백 등록")
self.future.add_done_callback(callback)  # ← 등록만 함, 실행 안 함

print("3. 요청 전송 완료")  # ← 즉시 출력됨
# 여기까지 빠르게 실행

# ========== while 루프 ==========
while rclpy.ok():
    rclpy.spin_once(node)
    print("4. 백그라운드에서 이 코드 계속 실행 중...")  # ← 계속 출력
    
    # 콜백은 여기서 언제든지 자동 실행됨
    # 서버가 응답하는 순간 "✅ 콜백 실행됨!" 출력
```

### 출력 순서

```
1. 요청 전송 시작
2. 콜백 등록
3. 요청 전송 완료
4. 백그라운드에서 이 코드 계속 실행 중...
4. 백그라운드에서 이 코드 계속 실행 중...
4. 백그라운드에서 이 코드 계속 실행 중...
✅ 콜백 실행됨! 응답: ... (이 시점은 서버 응답 속도에 따라 달라짐)
4. 백그라운드에서 이 코드 계속 실행 중...
```

## 🔄 서버 응답 전 vs 후

### 서버 응답 **전**
```python
self.future = self.client.call_async(self.req)
self.future.add_done_callback(callback)

# 이 시점에 콜백은:
# ❌ 등록됨
# ❌ 실행 안 됨
# ❌ future.result() 접근 불가

# 다만 future 객체는 존재함
print(self.future)  # <Future object>
```

### 서버 응답 **후**
```python
# ROS2 네트워크에서 응답 도착 감지
# ↓
# callback() 자동 실행

def callback(future):
    # ✅ 콜백 실행됨
    # ✅ future.result() 접근 가능
    response = future.result()  # ← 이제 값 있음
```

---

## 📊 상태 변화 테이블

| 시점 | future.done() | 콜백 | result() |
|------|-------------|------|---------|
| **요청 직후** | False | 미등록 | 불가 |
| **콜백 등록 직후** | False | 등록됨 | 불가 |
| **대기 중** | False | 대기중 | 불가 |
| **응답 수신** | True | 실행됨 | 가능 ✅ |

## ✨ 핵심 특징

### 언제 콜백이 실행되나?

```python
# ❌ 이 시점에는 실행 안 됨
self.future.add_done_callback(callback)

# ❌ 이 시점에도 실행 안 됨
print("대기 중...")

# ⏳ 이 시점에도 실행 안 됨
while rclpy.ok():
    print("계속 대기...")

# ✅ 이 시점에 자동 실행!
# "서버가 응답을 보냈을 때"
```

### 다른 작업과의 관계

```python
self.future.add_done_callback(callback)

# 콜백이 등록되었지만, 아직 실행되지 않음
while rclpy.ok():
    rclpy.spin_once(node)
    
    # 이 코드는 콜백 실행 전/후로 계속 실행됨
    print("메인 루프 계속 실행")
    
    # 콜백은 별도로 실행됨 (ROS2 이벤트 루프에서)
```

---

## 🎓 결론

| 질문 | 답변 |
|------|------|
| **콜백은 언제 등록되나?** | `add_done_callback()` 호출 시 **즉시** |
| **콜백은 언제 실행되나?** | 서버가 **응답을 보낼 때** |
| **응답 전에 다른 코드 실행?** | ✅ 예, 콜백 실행 대기 중에도 계속 실행 |
| **응답 받으면 콜백 자동 실행?** | ✅ 예, ROS2가 자동으로 호출 |
| **여러 요청 가능?** | ✅ 예, 각각의 future에 콜백 등록 |

# ✅ Subscriber & Timer 콜백 (Topic 기반)

## 개요

**Service 콜백**과 다르게 **Subscriber 콜백**과 **Timer 콜백**은 주기적으로 혹은 메시지 수신 시마다 자동으로 실행됩니다.

---

## 📊 콜백 종류별 비교

| 콜백 타입 | 트리거 | 호출 빈도 | 예시 |
|---------|--------|--------|------|
| **Service** | 요청 수신 | 1회 | 로봇이 특정 명령을 받을 때 |
| **Subscriber** | 메시지 도착 | 계속됨 | LIDAR 센서 데이터 수신 |
| **Timer** | 주기 경과 | 계속됨 | 0.3초마다 상태 확인 |

---

## 🔍 Subscriber 콜백 동작 원리

### 코드 예시

```python
from rclpy.node import Node
from sensor_msgs.msg import LaserScan
from nav_msgs.msg import Odometry

class RobotControl(Node):
    def __init__(self):
        super().__init__('robot_node')

        # Subscriber 생성: 메시지가 오면 콜백이 자동 호출
        self.odom_sub = self.create_subscription(
            Odometry,
            'mobile_base_controller/odom',
            self.odom_callback,  # ← 메시지 올 때마다 호출
            10
        )

        self.scan_sub = self.create_subscription(
            LaserScan,
            'scan_raw',
            self.scan_callback,
            10
        )

    def odom_callback(self, msg):
        """LIDAR 데이터 수신 시 자동으로 호출됨"""
        self.get_logger().info(f"Odom: {msg.pose.pose.position.x}")

    def scan_callback(self, msg):
        """Odometry 데이터 수신 시 자동으로 호출됨"""
        self.get_logger().info(f"Scan range: {msg.ranges[0]}")
```

### 시간 흐름

```
ROS2 네트워크
      ↓ (메시지 도착)
[1] Publisher가 /odom 토픽에 데이터 발행
      ↓
[2] ROS2 Middleware가 수신 감지
      ↓
[3] odom_callback() 자동 호출 ✨
      ↓
[4] Publisher가 /scan_raw 토픽에 데이터 발행
      ↓
[5] ROS2 Middleware가 수신 감지
      ↓
[6] scan_callback() 자동 호출 ✨
```

## ⏰ Timer 콜백 동작 원리

### 코드 예시

```python
class RobotControl(Node):
    def __init__(self):
        super().__init__('robot_node')

        # 0.3초마다 timer_callback() 호출
        self.timer = self.create_timer(
            0.3,  # 0.3초 주기
            self.timer_callback
        )

    def timer_callback(self):
        """0.3초마다 자동으로 호출됨"""
        self.get_logger().info("Timer tick!")
        # 로봇 상태 확인, 명령 발행 등
```

### 시간 흐름

```
시간선 →
  0ms   300ms   600ms   900ms   1200ms
   |      |       |       |        |
 tick   tick    tick    tick     tick
   |      |       |       |        |
   └─────┴───────┴───────┴────────┴──→
   timer_callback() 호출
```

## 🚨 Blocking Loop 문제: 원래 코드의 함정

### ❌ 문제 있는 코드

```python
def rotate(self):
    """10초간 로봇을 회전시키는 함수"""
    self.cmd_msg.angular.z = -0.4

    rotation_start_time = self.get_clock().now()
    rotation_duration = Duration(seconds=10)

    # ❌ 이 while 루프가 10초 동안 메인 스레드를 블로킹!
    while self.get_clock().now() - rotation_start_time < rotation_duration:
        self.vel_pub.publish(self.cmd_msg)

    # 이 10초 동안:
    # - odom_callback() 실행 안 됨
    # - scan_callback() 실행 안 됨
    # - timer_callback() 실행 안 됨
    # → ROS2 spin() 이벤트 루프가 블로킹되기 때문
```

### 실행 흐름

```
메인 스레드
├─ timer_callback() 호출
├─ rotate() 호출
├─ while 루프 진입 (10초 동안)
│  ├─ 발행... 발행... 발행...
│  └─ ... 10초 대기 ...
├─ rotate() 종료
└─ 이제 다음 콜백 처리 가능

문제: while 루프 중에는 다른 콜백이 처리될 수 없음!
```

## ✅ 해결책 1: State Machine 패턴 (권장)

### 핵심 아이디어

**Blocking loop 제거** → 상태 변수로 관리

### 구현

```python
class RobotControl(Node):
    def __init__(self):
        super().__init__('robot_node')

        self.timer = self.create_timer(0.3, self.timer_callback)

        # State Machine 변수
        self.is_rotating = False
        self.rotation_start_time = None
        self.rotation_duration = Duration(seconds=10)

    def rotate(self):
        """회전 시작 (blocking loop 없음!)"""
        self.is_rotating = True
        self.rotation_start_time = self.get_clock().now()
        self.vel_pub.publish(self.cmd_msg)
        # 즉시 반환

    def timer_callback(self):
        """주기적으로 상태 확인"""
        # 회전 중이면 시간 확인
        if self.is_rotating:
            elapsed = self.get_clock().now() - self.rotation_start_time
            if elapsed >= self.rotation_duration:
                # 회전 완료
                self.is_rotating = False
                self.stop_robot()
            else:
                # 계속 회전
                self.vel_pub.publish(self.cmd_msg)
            return

        # 회전 중이 아니면 레이저 데이터 기반 제어
        if self.front_laser > 0.5:
            self.move_straight()
        else:
            self.rotate()
```

### 장점
- ✅ **콜백 블로킹 없음** - odom, scan 콜백이 계속 실행
- ✅ **간단함** - Lock 필요 없음
- ✅ **실시간성** - 메시지가 오면 즉시 처리

### 단점
- ⚠️ 로직이 상태 변수에 분산됨

## 🔀 해결책 2: MultiThreadedExecutor + MutuallyExclusiveCallbackGroup

### 아키텍처

```
MultiThreadedExecutor (3개 워커 스레드)
├─ Thread 1: odom_callback (MutuallyExclusiveCallbackGroup)
├─ Thread 2: scan_callback (MutuallyExclusiveCallbackGroup)
└─ Thread 3: timer_callback (MutuallyExclusiveCallbackGroup)
```

### 구현

```python
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup
from rclpy.executors import MultiThreadedExecutor

class RobotControl(Node):
    def __init__(self):
        super().__init__('robot_node')

        # 각 콜백을 위한 독립적인 콜백 그룹
        self.odom_callback_group = MutuallyExclusiveCallbackGroup()
        self.scan_callback_group = MutuallyExclusiveCallbackGroup()
        self.timer_callback_group = MutuallyExclusiveCallbackGroup()

        # 각 subscription/timer에 다른 콜백 그룹 할당
        self.odom_sub = self.create_subscription(
            Odometry, 'odom', self.odom_callback, 10,
            callback_group=self.odom_callback_group
        )
        self.scan_sub = self.create_subscription(
            LaserScan, 'scan', self.scan_callback, 10,
            callback_group=self.scan_callback_group
        )
        self.timer = self.create_timer(
            0.3, self.timer_callback,
            callback_group=self.timer_callback_group
        )

def main(args=None):
    rclpy.init(args=args)
    control_node = RobotControl()

    # 3개의 워커 스레드
    executor = MultiThreadedExecutor(num_threads=3)
    executor.add_node(control_node)

    try:
        executor.spin()
    finally:
        executor.shutdown()
        control_node.destroy_node()
    rclpy.shutdown()
```

### 장점
- ✅ **병렬 처리** - 각 콜백이 독립적인 스레드에서 실행
- ✅ **응답성** - 한 콜백이 오래 걸려도 다른 콜백 처리됨

### 단점
- ❌ **Race Condition** - 공유 변수 접근 시 동기화 필요!
- ❌ **복잡함** - Lock/Mutex 구현 필수

---

## ⚠️ Race Condition 문제 (중요!)

### 문제 상황

```python
# Thread 1 (odom_callback)
self.front_laser = new_value  # 쓰기

# Thread 2 (scan_callback)
if self.front_laser > 0.5:    # 읽기 - 부분 업데이트된 값일 수도!
    ...

# Thread 3 (timer_callback)
self.is_rotating = True       # 쓰기
```

**MutuallyExclusiveCallbackGroup은 같은 그룹 내에서만 순차 보장!**
→ 다른 그룹의 콜백은 동시 접근 가능!

### 해결책: Lock 사용

```python
from threading import Lock

class RobotControl(Node):
    def __init__(self):
        super().__init__('robot_node')
        self.data_lock = Lock()
        self.front_laser = 0.0

    def odom_callback(self, msg):
        with self.data_lock:  # ← Lock 획득
            self.front_laser = msg.ranges[0]

    def timer_callback(self):
        with self.data_lock:  # ← Lock 획득
            if self.front_laser > 0.5:
                self.move_straight()
```

---

## 📈 3가지 솔루션 비교

| 항목 | State Machine | Multi-Thread Safe | Multi-Thread Unsafe |
|------|---|---|---|
| **구현** | SingleThreadedExecutor | MultiThreadedExecutor | MultiThreadedExecutor |
| **콜백 그룹** | 기본 (안 씀) | MutuallyExclusive | Reentrant |
| **스레드 수** | 1 | 2-3 | 2-3 |
| **Race Condition** | ❌ 없음 | ✅ Lock 필수 | ⚠️ 위험 |
| **안전성** | ✅ 최고 | ✅ 높음 | ❌ 낮음 |
| **복잡도** | 낮음 | 중간 | 중간 |
| **응답성** | 낮음 | 높음 | 높음 |
| **메모리** | 적음 | 보통 | 보통 |
| **권장** | ✅ **안전성 중심** | ✅ **균형** | ❌ **비권장** |

---

## 🎯 결론

### 언제 어떤 방식을 쓸까?

1. **State Machine (권장)**
   - 센서 기반 로봇 제어
   - 실시간성이 중요하지 않은 경우
   - 안전성이 최우선

2. **Multi-Thread + Lock**
   - 고성능 필요
   - 대기 시간이 길어도 다른 작업 계속해야 할 때
   - 동기화 구현 능력 있을 때

3. **Multi-Thread without Lock**
   - ❌ 절대 하지 말 것!
   - Race Condition으로 인한 버그 발생 가능
